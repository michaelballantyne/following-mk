# Size-bounded IDDFS: 1.6–88× wall-clock win over fair search, correctness preserved, ce-tuning inverts

Results for the design in `2026-07-14-012017-iddfs-search-design.md`.
Built + swept by a Sonnet agent (which died mid-sweep, its self-driving
sweep left retrying doomed configs); the advisor killed that, re-ran a
focused sweep directly, re-ran the fair arms fresh same-session for a
clean wall-clock comparison, and hand-verified every returned program.
Implementation commit: `07a03b9` (`dfs-search.scm` + 9
`experiments/*-full-id-views-dfs.scm` arms).

## Mechanism confirmed

The two-line `mplus` change ((mplus (f) f^) → (mplus (f^) f)) converts
the leader's per-level search from fair interleaving to depth-first.
Order-test proof: a two-clause infinite-tagged-stream query returns
`(a1 b1 a2 b2 a3 b3)` under fair `mplus` and `(a1 a2 a3 a4 a5 a6)` under
the DFS one (second clause never reached). Redefining top-level `mplus`
reaches `bind`/`conde` as the design predicted (flat top-level defines,
resolved at call time). Peak RSS ~32 MB vs fair search's GB-scale
allocation. The follower (settle) is untouched; `test-all` stays 114/114.

## Headline: wall-clock, same machine, same session

All answers are the correct canonical program, identical between fair and
DFS and between DFS ce1 and ce20 (bounds match per task). Wall-clock in ms;
`unify-main` alongside.

| task | fair ce1 (unify / wall) | DFS ce1 (unify / wall) | DFS ce20 (unify / wall) | DFS-best vs fair (wall) |
|---|---:|---:|---:|---:|
| rember | 328k / 10,588 | 260k / 10,572 | 1.88M / 4,426 | **2.4×** |
| append | 145k / 5,085 | 145k / 3,770 | 276k / 527 | **9.6×** |
| duplicate | 58k / 721 | 39k / 500 | 69k / 72 | **10×** |
| evens | 276k / 11,116 | 186k / 6,417 | 557k / 1,221 | **9.1×** |
| last | 115k / 4,079 | 91k / 2,735 | 1.30M / 2,286 | **1.8×** |
| member | 100k / 2,443 | 109k / 4,070 | 638k / 1,499 | **1.6×** |
| swap | 505k / 27,715 | 425k / 21,566 | 1.78M / 5,211 | **5.3×** |
| rev-acc | 133k / 39,394 | 58k / 1,841 | 273k / 447 | **88×** |
| interleave | 116k / 3,147 | 99k / 2,004 | 437k / 659 | **4.8×** |

**Every task is faster under DFS, best-case 1.6× to 88×.** rev-acc is the
standout: 39.4 s → 0.45 s. It was the most follower-heavy task under fair
search (the growing accumulator makes evalo/d env-plumbing dominate, and
fair interleaving churns enormously over it); DFS with the size bound
walks straight through it. DFS ce1 alone (no tuning) already beats or ties
fair on every task; ce20 is the sweet spot.

## The answer to Michael's question: yes, IDDFS helps wall-clock, substantially

The hypothesis — DFS's lower per-node overhead (no interleaving
round-robin, far less suspension-thunk churn) cuts wall-clock while
size-frontier iterative deepening preserves minimality — is confirmed on
all 9 tasks. And the correctness half held: **the four tasks the
fair-search-*without*-ID sweep silently broke (last, member, duplicate,
rev-acc — `...-193454`) all return the correct canonical recursive program
here**, hand-verified by substitution on length-4+ inputs, because
size-frontier IDDFS keeps the smallest-answer-first guarantee. So IDDFS is
the double win the design predicted: fast like DFS, correct like
size-closed ID.

## unify-main and wall-clock DIVERGE — a methodological note

On several tasks DFS ce20 does *more* `unify-main` than fair yet is much
faster in wall-clock (rember 1.88M vs 328k → 2.4× faster; last 1.30M vs
115k → still faster). The project's traditional "work" metric
(unify-main) and wall-clock are measuring different things here:
fair-interleaving wall-clock is dominated by suspension-thunk
allocation/GC per unit of logical work, not by unify count. DFS trades a
higher raw unification count for drastically less allocation and
scheduling overhead. At ce1 DFS wins on *both* (fewer unifications *and*
less overhead); at ce20 it wins on wall-clock while spending more
unifications. Consequence: **for wall-clock claims, measure wall-clock** —
unify-main is not a faithful proxy across a search-strategy change. (It
remains the right perturbation-immune metric for comparing *pruning* under
a fixed strategy, which is what it was introduced for.)

## The ce-tuning story inverts vs fair search

Under fair search (`...-193454`), `check-follower-every=100` (fire rarely)
was fastest — interleaving papered over divergence and infrequent firing
saved per-fire overhead. **Under DFS it is exactly reversed:**

- **ce100 is catastrophic.** With the follower firing rarely, nothing
  prunes doomed branches early, so DFS exhaustively grinds each entire
  size level. rember ce100 spent 9M → 30M → 96M `unify-main` on bounds
  31/35/39 (none of which even contain the answer) before we killed it;
  8 of 9 tasks' ce100 hit the 90 s cap without an answer (duplicate ce100
  finished only because its answer is small, at 229× the work of ce1:
  9.0M vs 39k). The follower's pruning is what keeps a DFS level finite in
  practice.
- **ce1 is safe but pays per-fire overhead** (fires every conde → high
  unify-follower; rember ce1 7.5M follower-unify).
- **ce20 is the sweet spot**: enough pruning to avoid the level explosion,
  little enough per-fire overhead to be fastest on every task.

This is a real operational finding: the right `check-follower-every`
depends on the *search strategy*, oppositely for DFS vs fair, and it is
not a safe correctness dial (correctness comes from minimality, which
holds at every ce here — ce1 and ce20 return identical answers; only speed
varies).

## Caveats / what this does NOT yet establish

- **Per-level termination still leans on `*main-unsound-depth*` (=1000) as
  the guaranteed backstop**; in practice the views cut divergent branches
  first (depth-cut 0 on the completing runs). No level *hung* — the ce100
  slowness is exhaustive grinding, not divergence — but a task whose views
  don't refute a divergent family would expose DFS's fragility more than
  fair search does. Not seen on these 9.
- **The suspension machinery is still present.** DFS `mplus` removes the
  interleaving round-robin but `fresh`/`conde` still wrap bodies in
  `suspend` thunks. The measured win is from killing the round-robin; a
  bespoke stack-based DFS with no `suspend` at all could go further, but
  the design deliberately measured the minimal change first — and the win
  is already large enough (1.6–88×) that the bigger rewrite isn't
  obviously warranted. Revisit only if a task stays wall-clock-bound.
- ce100 numbers are capped at 90 s (documented catastrophic, not run to
  completion) — deliberate, to avoid burning ~90 min re-confirming the
  obvious.

## Bottom line

Size-bounded IDDFS should become the default search for these synthesis
tasks: uniformly faster wall-clock than fair-interleaving size-closed ID
(the prior "current best"), correct on all 9 (unlike fair-without-ID), at
`check-follower-every` ≈ 20. The `-dfs` arms are the reference
configuration going forward. Natural next step: make ce20-ish the default
in the arms and re-baseline, and consider whether the explicit-scheduler
backlog item (which would read the residual frontier directly) is still
worth it now that a two-line DFS `mplus` already captured most of the
wall-clock available from dropping fair interleaving.
